# PaperQuay UI 逻辑与视觉优化计划

- 日期：2026-11-02
- 状态：**阶段 1、2 完成；阶段 3 的 12/13/14/15 完成**
- 范围：渲染层界面结构与交互逻辑、设计令牌与视觉一致性、共享 UI 原语、无障碍与键盘通道；不涉及后端数据模型与 AI 能力
- 关联：`docs/changes/README.md`（实施后按格式补变更记录）、`docs/USER_MANUAL.zh-CN.md`（若有交互变更需同步）、`docs/notes-charter.md`（笔记工作区规范不得违背）

## 结论

界面逻辑与视觉都存在可优化空间，但两者性质不同，需分开处理，且优先级应由"冲突面"而非"重要性"决定。

1. **有一个在特定布局下必然触发的可用性缺陷，不是审美问题。** 文库列表卡片在侧栏拉宽后，标题、作者、期刊、路径全部被压成 0 宽度而不可见，卡片只剩年份与日期，徽标被挤成竖排，单卡高度被撑到约 300px 却几乎全是空白。根因是固定列布局配上"视口断点"，而该区域是可变宽的容器（详见下节）。
2. **交互逻辑缺少三样基础设施**：统一反馈层（无 toast、全仓库 `aria-live` 为 0）、统一浮层原语（11 个文件各自实现 `fixed inset-0` 遮罩，另有 2 套确认框）、统一命令与快捷键入口（无任何快捷键注册表）。无障碍方面 `focus-visible` 仅出现在 3 个文件、CSS 中 0 处。
3. **视觉层的主要问题不是审美不足，而是设计系统失控**：令牌体系已经建好（902 处 `var(--pq-*)` 引用），但 48 个文件里另有 691 处硬编码 Tailwind 调色板绕过它；`index.css` 里还写了 `.pq-saas-scope` 属性选择器强行把这些硬编码色改回正确值，属于为漂移打的补丁。同一品牌 accent 浅色为 `#0d9488`、深色为 `#86a89f`，跨主题色相与饱和度不连续。
4. **中英混排是系统性问题，不是零星遗漏**：除 1410 处内联 `l('中文','English')` 之外，笔记编辑器有一张混着中文与未翻译英文的 `TEXT` 表（`NoteEditor.tsx:287-305`），Agent 界面直接写死英文单位 `tok`。结果是中文界面稳定出现英文标签，且与语言设置无关。
5. **缺少设计规范文档**，导致上述漂移无法在审查阶段被发现，只能靠事后截图或用户反馈发现。

据此建议分三阶段推进：先修可验证缺陷（局部、低冲突），再补交互基础设施（以新增文件为主），最后做结构性重构（大面积改既有文件，必须独占上游同步周期）。本仓库 `main` 跟随 `WangQrkkk/PaperQuay` 同步，大范围重写会让每次 `upstream` 合并都变成手工解冲突，这是排序的主要依据。

## 调研方法

1. 源码静态分析：布局容器、设计令牌、i18n 调用、浮层与无障碍实现、交互状态流。
2. 实机观察：以安装版（与本仓库同为 v0.4.16，工作区干净）运行，逐一截图文库、阅读器、Agent、笔记、知识图谱、设置六个界面，并在最大化与原始窗口两种尺寸下复核。
3. 数值核对：将截图中的实际列宽与代码中的固定列宽相加，验证"标题被压没"是几何必然而非渲染偶发。

截图保存在会话工作台 `shots/` 目录，**未纳入仓库**：这些截图包含个人文库文献标题与笔记正文，不适合提交到公开仓库。文档内的结论均已写成可复核的文字与数值，不依赖截图存在。

### 卡片塌陷的几何计算

`src/features/literature/components/LiteraturePaperList.tsx:694-695` 定义卡片列：

```text
grid-cols-[28px_minmax(0,1fr)_minmax(128px,160px)_72px_96px]  // 开启热力列
max-[900px]:grid-cols-[28px_minmax(0,1fr)_64px_86px]          // 降级分支
```

- 固定列开销：`28 + (128~160) + 72 + 96 = 324~356px`，再加 4 个 12px 间距 = **372~404px**。
- 实测布局：窗口 1568 CSS px，侧栏 377 + 详情栏 628 后，列表容器约 445px，留给 `1fr` 标题列仅 **41~73px**。标题、作者、路径均带 `truncate`，被截成不可见；徽标容器 `flex-wrap` 一行一个，卡片高度被撑到约 300px。
- 降级分支用 `max-[900px]:`，这是**视口媒体查询**；窗口宽 1568px 时永不命中。真正变窄的是容器，断点判断对象错误 —— 这是根本原因。
- 窗口缩到最小宽 1040 时，列表被 `minmax(360px,1fr)` 压到 360px，而固定列开销 372~404px 已经超出，**必然塌陷并横向溢出**，与用户是否手动调整过侧栏无关。

实施中的两处方案修订：

- 图谱标签原定用 `min-zoomed-font-size` 做缩放阈值。实机验证发现无效：隐藏标签会让节点包围盒变小，`fit` 随即放大视图，标签又重新满足显示条件，形成反馈振荡，总览仍是一片重叠文字。改为**数据驱动抽稀**：总览只标注前 20% 的 hub（节点数 ≤ 40 时全标），选中节点强制标注，用户放大到 1.15 倍后恢复全部标签。
- 「导出批注 PDF 浮层压正文」经代码核对与实际截图确认为误判（工具栏为文档流换行布局，与 PDF 画布有真实间隙），已撤回不改。

遗留：卡片条目的 Ctrl 多选、拖拽排序、拖到分类需要修饰键或拖拽手势，Cua 在该窗口的后台输入不支持修饰键（返回 `refused`），未验证；本次未改动事件处理。

## 已定选择（2026-11-02 用户认可）

以下五项已确认，实施时按此执行，不再重议。

| # | 问题 | 已定方案 | 依据 |
| --- | --- | --- | --- |
| 1 | 阶段顺序 | **按现计划顺序：P0 → P1 基础设施 → P2 视觉统一** | 卡片塌陷是可用性缺陷，先止损；且 P2 会重写设计层，先做视觉统一等于把 P0 的修复重构一遍。另需在 P2 之前落地 Dialog/Menu/Toast 原语，否则视觉统一没有可复用的承载物，容易返工 |
| 2 | 首次引导 | **删除 `data-tour` 死代码，不做好引导**；把同等投入放到空状态与命令面板 | 本项目是个人二次开发、单一使用者，引导的产品价值接近零；而布局每次调整都要同步维护引导步骤。命令面板对熟练用户等于"可发现的引导"，且能长期复用 |
| 3 | 密度开关 | **不引入全局密度开关**，改为「容器自适应 + 默认收紧信息层级」 | 卡片当前最多可堆 7 行信息（主标题、副标题、作者、3 个徽标、标签、路径），问题在层级而非用户偏好。两档密度会让每个界面的测试面翻倍（2 档 × 6 界面 × 2 主题 × 3 窗口宽），对单人维护成本过高；容器查询已能自动适配 |
| 4 | accent 统一 | **以浅色 `#0d9488` 为品牌基准，深色用同色相提亮变体**（起始值 `#2dd4bf`，按钮底 `#115e59`）；同时把 `--pq-success` 改为偏纯绿（浅 `#16a34a` / 深 `#4ade80`） | 现有深色 accent `#86a89f` 已从 (174.7°, 84%, 32%) 变成 (164.1°, **16%**, 59%)，饱和度塌到 16%，与浅色不是同一颜色。更关键：浅色 accent (174.7°) 与 success `#059669` (161.4°) 只差 13°，饱和度与亮度几乎相同，导致「强调」与「成功」无法区分（截图中 MinerU 已解析与 RAG 已索引两种徽标同色）。success 移到 142° 后可拉开 30° 以上 |
| 5 | 变更记录粒度 | **卡片塌陷单独一份，其余 UI 小修合并为一份** | 卡片条目信息量大（复现步骤 + 几何根因 + 前后对比），将来可能被单独引用；笔记遮挡、设置表单、命名消歧、中英混排属低风险视觉修正，逐条拆分会稀释检索价值。两份都反向链接本计划文档 |
